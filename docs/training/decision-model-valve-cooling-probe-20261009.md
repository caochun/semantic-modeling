# 姑苏站阀冷日志：Decision Model 实测与训练来源核查

日期：2026-10-09。案例：用户提供的 2026-09-11 12:36:14 至 12:48:35 共 20 条日志。来源范围仅为 `rawdoc/姑苏站`。

**结论：当前两份试点模型都不能可靠完成这一判断。现有文档包含可以补充训练的运行规则、故障判据和同设备历史事件，但尚不足以将这次日志标成“确定正常”或“确定故障”。**

## 1. 实际测试了什么

加载两台服务器已经保存的 `unsloth/Qwen3.5-0.8B` LoRA 与 Clef 决策头，使用官方 `FastDecisionModel.predict` 实际推理：

- 192.168.30.134 / RTX 4090：`gusu_alarm_20261009/attempt03/pilot/adapter`。
- 192.168.30.194 / TITAN V：`gusu_alarm_20261009/attempt02/pilot/adapter`。

这是选择型 Decision Model，不生成自由文本分析。此次新增 `system_status` 问题，三项候选含义是：

1. **确认异常**：已有足够证据确认设备故障、真实泄漏或保护异常。
2. **正常过渡**：已有足够证据确认是符合控制逻辑的风机调节与短时屏蔽，所给过程未见异常。
3. **证据不足**：不能在前两项中确定，需要补充状态或适用控制逻辑。

两种输入条件分别是全部 20 条日志，以及相同日志加规程三的原文摘录（一般监视要求、奇偶风机分组、变频/工频切换、轮循启停和整组切换）。摘录没有添加分析者的结论，也没有把“10 分钟屏蔽”假设作为规则输入。后一条件仅检验这组具体摘录的帮助，不代表检索全部文档后的能力上限。

每种条件做三次循环换位，只改变三个候选语义与 `c0/c1/c2` 的对应关系。共 2 个模型 × 2 种输入 × 3 种换位 = **12 次预测**，不是 12 个独立业务案例。

| 输入 | 选项换位 | .134 实际选择 / API confidence | .194 实际选择 / API confidence |
| --- | --- | --- | --- |
| 仅日志 | 0 | 正常过渡 / 0.5082 | 正常过渡 / 0.8296 |
| 仅日志 | 1 | 确认异常 / 0.9852 | 确认异常 / 0.9917 |
| 仅日志 | 2 | 确认异常 / 0.9998 | 确认异常 / 0.9996 |
| 日志＋规程摘录 | 0 | 正常过渡 / 0.9888 | 正常过渡 / 0.9969 |
| 日志＋规程摘录 | 1 | 确认异常 / 0.9734 | 确认异常 / 0.9920 |
| 日志＋规程摘录 | 2 | 确认异常 / 0.6287 | 确认异常 / 0.7948 |

两种输入条件下，两份模型均随候选换位改变语义结论，均未选择“证据不足”。这种不稳定足以否定当前输出的可靠性；本例没有专家金标，不能据此计算准确率。API confidence 使用试点保存的温度校准，该小校准集已有过拟合现象，不是现场正确率。99.98% 的数值也不能证明结论正确。

全部输入保留完整内容：仅日志 1734 token，附规程 2227 token，都低于训练配置的 4096 token，没有截断。换位之间 token 数不变。已核对请求文件 SHA256、返回选项到语义的映射和固定上游代码哈希。

原训练集仅有 18 个规则族、43 个模拟场景，主要训练 `blocking` 与 `next_check`，输入含适用规则；没有训练本次阀冷事件窗口异常分类。此次结果说明该试点尚未泛化到此任务，不能据此断言整个 Decision Model 方法无效。

## 2. 对这组日志的证据分析

以下是日志计算及文档核对的结果，**不是上述模型生成的解释**。

| 通道 | 退出运行信号的风机 | 相邻事件间隔（秒） | 屏蔽出现至消失（秒） | 最后风机事件至屏蔽消失（秒） |
| --- | --- | --- | --- | --- |
| B2 / P221VCC2 | E4.M01 → M03 → M05 | 9.325、10.395 | 619.489 | 599.769 |
| A2 / P221VCC2 | E4.M01 → M03 → M05 | 9.277、10.610 | 618.910 | 599.094 |
| A1 / P221VCC1 | E2.M02 → M04 → M06 | 10.330、10.281 | 619.491 | 598.880 |
| B1 / P221VCC1 | E2.M02 → M04 → M06 | 9.603、10.477 | 618.580 | 598.591 |

规程三“阀冷系统 → 外水冷系统运行规定 → 变频风机运行规定”明确：

> 阀外冷系统共配置6台变频风机，分为2组（M01、M03、M05为一组，M02、M04、M06为一组）。
>
> 变频风机控制采用先起先停、先停先起的轮循启停控制策略。
>
> 单组风机运行时，风机具有定时切换、整组故障切换、整组手动切换功能。

上述分组与日志对应，约 10 秒的顺序变化、约 10 分钟后的屏蔽解除，支持“控制过程导致一组风机依次退出，同时发生暂态屏蔽”这个待验证解释。**定时切换、手动切换和故障切换均可能产生状态变化，仅有顺序性不能区分原因。**

现有证据下适当的回答是：**观察到了风机运行信号退出和泄漏保护短时屏蔽，尚不能据此确认设备故障或真实泄漏；也不能确认系统正常。应补充控制指令、其他风机状态、相关故障事件及水冷参数，并核对屏蔽逻辑。**

具体边界：

- “风机运行消失”表示运行指示撤销，不能直接改写成“风机故障”，也不能理解为“故障已恢复”。
- “泄漏保护短时被屏蔽出现/消失”描述屏蔽状态，不等于“泄漏出现/消失”；也不能据此确认所有保护恢复正常。
- 日志没有提供完整风机状态快照或另一组投入记录，不能推出“所有风机全停”。
- A/B 时序相近且设备规程有冗余控制结构，但需点表确认映射；不能把两个通道直接算作两倍物理故障。
- `alarm_level=3` 没有配套字典，本次未解释为轻重等级或“正常”。
- 约 600 秒是相对**最后一个风机事件**计算的；相对首次屏蔽出现约为 619 秒。尚未找到触发、重触发及解除计时的明确条款，不能写成“规定 600 秒，超过就异常”。
- 这 20 条中未出现故障/液位告警，不等于完整事件流里不存在这些告警；更不能用于判断全站其他系统。

优先补充：事发前后完整事件窗口、风机控制模式与启停/切换命令、其他风机运行状态、变频器/电源及冗余能力告警、进出阀温度/膨胀罐液位/流量趋势、实际生效的阀冷软件逻辑与点表。

## 4. 补充训练集的具体方向

建议建立独立的阀冷事件窗口数据集；现有来源足以开始做候选样本，不应直接复制规程生成一批无条件“正常/异常”标签。

1. **观察与原因分开。** 标注运行指示、故障指示、屏蔽状态、恢复状态，以及各自时间；原因只在有控制命令、规程或现场记录支持时标注。
2. **按完整窗口判断。** 输入包括窗口前的状态、完整事件、适用规则及关键模拟量；提供“窗口发生过异常”与“窗口末仍有异常”两个不同问题。
3. **形成有区分力的对照。** 正常调节须有指令和运行状态佐证；故障样本包含故障/冗余能力事件；信息不足样本缺少关键状态；屏蔽超时样本必须等实际计时逻辑确认后再构造。
4. **保留自然历史与合成样本来源。** 调试模拟故障标明模拟背景；规则派生样本明确是合成，不能冒充现场事件。当前用户案例留作独立回归评测，不纳入训练。
5. **按完整事件/试验及规则族划分。** 同一事件的A/B通道、相邻窗口、不同表述和选项排列不得跨训练与评测集合，避免泄漏。
6. **验证语义稳定性与保留不确定性。** 训练时平衡标签并变化选项顺序，评测检查换位一致性、删除故障证据后的响应、异常漏报及“证据不足”选择；校准须使用足够的独立窗口，不能靠高 confidence 验收。

这次只新增测试脚本、独立案例、推理结果与来源报告；冻结的 v1 训练集、已有权重、应用数据均未改变，没有启动新训练。

## 5. 复现与产物

测试入口：[probe_case.py](../../experiments/decision_model/probe_case.py)。在已安装固定版本的 GPU 环境、仓库根目录执行：

```sh
python -m experiments.decision_model.probe_case \
  --adapter /实际路径/pilot/adapter \
  --requests experiments/decision_model/cases/gusu-valve-cooling-20260911/requests.json \
  --output /新结果路径/result.json
```

案例目录：[gusu-valve-cooling-20260911](../../experiments/decision_model/cases/gusu-valve-cooling-20260911)。

- `raw.tsv`：20 条用户日志的全部字段值；只统一分隔符和外层引号。
- `case.json`：案例来源、三类候选含义、无专家金标声明。
- `requests.json` / `evidence.json`：实际六组请求和提供给模型的原文摘录。
- `timing.json`：仅供分析的时差计算，未混入模型输入。
- `result-host134.json` / `result-host194.json`：完整 API 输出、长度、模型配置和权重文件哈希。
- `source_review.json`：补充训练来源的原文与定位，范围大于本次输入模型的摘录。
