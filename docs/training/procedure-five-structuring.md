# 规程五的完整结构化与可执行规则边界

## 目的

规程五不是只包含当前已经实现的 4 条核查规则。当前实现把它分成两层：

1. **完整条款索引**：把 Markdown 转写中的全部编号单元保存为带来源定位的结构化记录。
2. **可审计决策规则**：从已经经过业务整理的高价值章节中，提取可用于现象核查的触发条件、缺失证据和规程引用。

因此，“完整结构化”表示全文可检索、可定位、可回溯；它不表示系统已经把每一句规程自动翻译成可以直接执行的操作指令。


`parent_clause_id` 表示编号树中的直接父级；`scenario_clause_id` 表示所属的二级异常预案；`section_clause_id` 表示该记录所属的最近现象、处理或其他章节段落。正文、重复提示、条件限定语和原文中的疑似笔误均保留，便于人工复核。

原 Markdown 中少数“处理原则”使用加粗编号行表示，没有使用 Markdown 标题。索引保留这些记录的 `kind: clause`，同时以 `section_marker: true` 把它们作为处理段的层级锚点；例如 `11.3.2` 能正确成为 `11.3.2.4` 的处理段。

## 现有可执行规则

当前 `experiments/decision_model/procedure_rules_v1.json` 中有 4 条规则：

- 10.3：内水冷泄漏候选的证据核查；
- 10.4：内水冷主循环泵故障后的核查；
- 10.5：主泵异常且备用泵未投入的核查；
- 11.3（同时引用 11.1）：阀外水冷风机运行反馈丢失后的核查。

全文索引的 `coverage` 字段记录规则与源文的映射。当前 4 条规则均为 `linked`，并保存对应的 Markdown 行、PDF 页和原书页码。

规则层只输出当前证据支持的现象、需要补充的核查项和证据不足状态。例如，“泄漏保护短时被屏蔽”可以触发对泄漏证据的核查，但不能单凭这一条日志判定现场已经发生物理泄漏；“报警消失”也不能直接等同于设备恢复。

## 为什么不直接把 1,903 条转换成动作规则

规程中的处理条款经常包含以下内容：

- 多个条件分支和先后顺序；
- “经领导批准”“申请调度”这类授权前置条件；
- 停运、隔离、退出保护、切换电源等高风险操作；
- 需要现场检查、仪表趋势或其他系统状态才能成立的条件；
- 重复条款、编号异常和版本适用范围。

这些内容必须先拆成可验证的观察条件，再由运行专业人员确认条件、权限和操作边界。未经拆解的原文不应直接作为自动执行策略，也不应直接当作训练金标。

## 下一步：从场景模型到决策分支

第 10、11 章中的每个二级预案现在都可以作为一个独立场景入口。后续应先按 `scenario_clause_id` 聚合现象和处理条款，再为每个场景补充日志信号映射和缺失证据状态。这样同一条日志可以先定位到异常场景，再进入对应的核查分支。

## 从全文索引到决策分支的后续过程

对每个优先章节，建议按下面的顺序处理：

1. 从 `phenomenon` 段提取可由日志或监控信号识别的现象，并建立信号标准化映射。
2. 从 `treatment` 段拆分条件、检查、禁止事项、授权前置和建议动作。
3. 将每个条件绑定到原文条款和页码，标记 `observed`、`missing`、`contradicted` 或 `not_applicable`。
4. 为分支建立人工审核的规则测试，验证边界条件、缺失数据和冲突信号。
5. 只有在规则完成业务复核后，才将其加入 `procedure_rules`，供现象识别和核查建议使用。

推荐的章节推进顺序是：10 阀内水冷、11 外水冷、8 控制系统、9 保护和远动、12 站用电，之后再处理电网事故、换流变、GIS、交流滤波器、直流场及辅助系统。
